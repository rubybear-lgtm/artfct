# Spec 32: Context post skill (RUB-553)

**Track:** Context posts (RUB-551 epic) · **Depends on:** 29 (post data schema, RUB-559), 27 (first-class types, RUB-575 `post` case) · **Blocks:** RUB-556, RUB-554, RUB-568, RUB-577, RUB-573 (merge order in RUB-551, decision 8)

This page is both the spec and the plan.

## What and why

A bot that is asked to publish a pricing decision or a weekly announcement should load one official skill, fill a fixed post shape, deploy it as a `post`, and run one findability check. The skill ships as a guidance topic, the same way `kanban`, `team-wiki` and `announcements` do (RUB-551 decision 1).

The skill is written against the data from spec 29. Owner, status and replaced-by live in `post/details`. The page's `post-details` block is a display snapshot for search and for readers without JavaScript. A bot that changes state writes `db_update` first and republishes the snapshot second.

## Decisions

- **Version stays `1.5.0`.** The base already moved `ArtifactGuidance::VERSION` from `1.4.1` to `1.5.0` in RUB-575. `main` is still `1.4.1`, so the merged change is `1.4.1 -> 1.5.0`, which is what the Done-when asks for. This issue adds a topic under the same version. Owner's call whether that should be a separate bump.
- **Snapshot block is `<dl class="post-details" data-post-details>`** with five rows: Kind, Owner, Date, Status, Replaced by. The 29 starter wrapped the `<dl>` in a `<section>` and had no Date row, so the starter is aligned in this issue (the page-side half of the Done-when).
- **Date is not a data field.** Spec 29 has four fields. Date is the day the post was first published, written by the bot into the snapshot as `YYYY-MM-DD` and kept unchanged on later republishes. It is not stored in `post/details`. Adding a field would change spec 29's validation, which is out of scope here.
- **Display case, data case.** Data values are lowercase (`decision`, `current`). The snapshot shows title case (`Decision`, `Current`). The starter's `app.js` capitalises the first letter of `kind` and `status` for display. A bot writes data values to `db_update`, never title-case values.
- **Replaced by.** Data holds an artifact id. The snapshot holds a link to the newer post's `view_url` (from `deploy_artifact` or `get_artifact`), or the text `None`. `app.js` leaves an existing link alone unless the data is null, so the link is not replaced by a bare id.
- **Seeds apply on first deploy only.** The guidance inlines the full db manifest (both collections, both indexes, and the `details` seed) so a connector-only host can pass it to `deploy_artifact` without reading a file. Later changes go through `db_update`.
- **Supersede order:** publish the new post and take its id and `view_url`; `db_update` the old post's `status` to `superseded` and `replaced_by` to the new id; republish the old post with `artifact_id` and `base_version`.
- **`db_update` has no `if_version`.** Its schema takes `id`, `collection`, `doc_id` and `data`. The guidance names only those.
- **Skill files.** `skills/artfct-context-post/SKILL.md` sits at the skill root, next to the existing `assets/post-starter/`, because the mirror test reads that path. It is hand-written (not routed through `TemplateSkillSync`). It is generated by concatenating the frontmatter with `resources/guidance/context-post.md`, so the mirror is byte-exact.
- **Plugin pack.** `artfct-context-post` is added to `PLUGIN_SKILLS` in `scripts/plugin/sync-skills.mjs`, next to `artfct-announcements`, so the plugin ships the skill and its starter.

## Guidance rules (served text)

The guidance tells the bot, in order:
1. Search the library for the same topic with `search_artifacts`.
2. `read_artifact` anything it relies on, and cite its id and version.
3. If an existing post covers the same decision, update it with `artifact_id` and `base_version` instead of publishing a duplicate.
4. Declare the `post` collections in the db manifest and seed `details` with the real kind, owner and status.
5. On supersede, follow the order above.
6. Deploy with `artifact_type: post` and a two-to-four-word title.
7. Run one findability search with `search_artifacts` and stop.

It also says: if the owner or the decision cannot be taken from the person's words, ask them; never invent an owner. It points at `artfct-announcements` for pulling an announcement board, so the two topics are not confused.
